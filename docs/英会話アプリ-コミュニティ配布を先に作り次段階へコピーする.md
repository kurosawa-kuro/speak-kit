## 二つのリポジトリ

分離は最低二つである。同じリポジトリにしない。

| | 推奨リポジトリ名 | いつ作るか | 中身 |
|---|---|---|---|
| 現行 | （private-ops 内のまま） | すでに live | Phase 1 の毎日の学習。二つの変更を受け取らない |
| 1 | `speak-kit` | 最初 | 英会話コミュニティへ配るアプリ。参照元は `private-ops/apps/skill-trainer`。挙動・SQL・文言はコピーし、Rust API は Next.js へ書き直す。実行基盤は crate・Retool・ローカル Postgres にしない |
| 2 | `speak-next` | `speak-kit` ができてから、そのコピー | Phase 2 移行の発展アプリ。将来 private-ops へ吸収・反映する可能性あり |

コピーした時点で `speak-next` は別リポジトリになる。その後の変更は `speak-kit` へ戻さない。`speak-kit` は配る相手のアカウントで動かす。`speak-next` は黒澤の Phase 2 開発である。相手の利用量と、黒澤の学習データ・鍵を同じ置き場に載せない。

### リポジトリ名

2026-10-13 の推奨。小文字のケバブケースで、手元の `private-ops` や `ai-gateway` と同じ並びにする。

`speak-kit` は、コミュニティの人が GitHub と YouTube で見る名前である。各自が自分のアカウントで立てる一式、という意味が名前に出る。`private-ops`、`skill-trainer`、Phase 番号は入れない。

`speak-next` は、コピーしたあとの発展側である。配る相手が発展側を fork しにくい。`phase2` を名前に入れると、面接の次へ進んだときに古くなる。`skill-trainer` とも別名なので、将来 private-ops へ入れるときに既存アプリと衝突しない。

代替は次の二つ。推奨を棄却したわけではない。

- 系統を名前で残す場合、発展側だけ `speak-kit-next` にする。配布側は `speak-kit` のまま。
- コア機能を名前にする場合、配布側 `phrase-practice`、発展側 `phrase-practice-next`。フレーズ練習としては明確だが、発展側は外資面接まで育つので `phrase` は発展側には狭い。

### 学習データ

live の学習者 Evidence は現行データベースに残る。`speak-next` は開発中、そのデータベースへ書かない。発展側で別の推定を育て、吸収の日に一人の学習者の Evidence を二つにしない。採点や計画の修正を、live の学習を止める形で両方へ同時投入しない。吸収時に何を反映し、何を捨てるかは未決。

学習者を Phase 2 へ進める判断は、リポジトリの有無とは別に行う。設計正本は、エンジンが動いていることだけでは Phase 2 を始めず、学習者 Gate、Phase 1 の実測、追加する教材の質を分けて見る。

`speak-next` は設計正本の Phase 2（外資面接）を作る場所である。正本は「別アプリにはしない」と書いている。開発中は private-ops の外に置き、吸収したあとの製品の形として、その一文を残す。吸収しないまま残す判断も、ここではしない。

## speak-kit

作業順の最初に作るリポジトリ。英会話コミュニティの知人に、個人の英会話練習アプリを Github 経由で渡す。実行基盤は本番 `skill-trainer` の crate・Retool・ローカル Postgres ではない。実装時の参照元アプリは `/Users/kurosawa/Dev/private-ops/apps/skill-trainer` であり、挙動・SQL・ドメイン文言は限りなくコピーで済ませる。Rust の API はフル Next.js ではそのまま載せられないので、同じ挙動を Next.js API Routes へ書き直す。技術スタック、配布、AI キーが死んでもコアが動く設計を、この節に置く。

**owner 決定（2026-10-11）**: 渡した相手のアカウント（API キー・ホスティング・DB など）はすべて黒澤本人から切り離す。黒澤名義の課金・鍵・DB に相手のアクセスや利用量が乗らない構成にする。構築・運用の手順自体は YouTube 動画として公開する。

private-ops の個人運用（P9＝ローカル Postgres 正本、無料枠原理、API-less 構成）とは別物である。知人は各自が自分の一人用インスタンスを立てる。一つのインスタンスを不特定の人へ開く公開アプリではない。private-ops の既存ルールをそのまま適用する対象ではない。本番 `skill-trainer` の Rust エンジン・Retool 画面・ローカル Postgres は、このアプリの実行基盤にはしない。挙動の参照元にはする。

対象:

- 独立 Github リポジトリ（private-ops とは別 repo）
- 対象ユーザーは英会話コミュニティの知人。各自が自分用のインスタンスを一つ立てる
- 公開範囲は、そのインスタンスを誰が使えるか、である。決定は利用者一人のプライベートアプリ。AI キーの悪用防止のため、複数人や誰でも使える形にはしない
- 英会話練習はテキスト。音声入出力は作らない。コア機能は AI キー無しで動作し、Claude API は任意オプション
- AI 機能が未設定・失効・レート制限・到達不可でも、コア操作が最後まで通る安全設計
- アカウント作成からデプロイ、日常運用までの手順を YouTube 動画として公開する

対象外: private-ops の既存アプリとの結合、live への書き戻し、本格的な商用化、AI 機能自体の品質（フィードバックの精度）。参照元からの挙動・SQL・ドメイン文言のコピーは対象である。ここは「無くても壊れない」ことだけを扱う。

### 誰の API キーで動かすか

配布型で確定する。

| 案 | 内容 | 評価 |
|---|---|---|
| 単一ホスト型 | 自分がホストして友人に共有。自分の Anthropic キーに課金が乗る | **不採用**。アカウント完全分離と矛盾する |

クオータ制限（単一ホスト型特有の課金リスク対策）は不要である。各人が自分のキー・自分の無料枠で動かす。重要になるのはセットアップの再現性である。「Deploy with Vercel」ボタンと Github テンプレートリポジトリ化で、clone・fork・env 設定の手数を最小化する。

配布型では、キー未設定・入力ミス・キー失効・無料枠超過がデプロイ直後から日常的に起こる。AI 呼び出しの失敗がコア機能（テキストのフレーズ練習、学習記録）を巻き込んで落とす設計は、配布先の非技術者にとって致命的である。各インスタンスは利用者一人に閉じ、他人が AI キーを使えないようにする。

### AI 機能の安全設計

対象は、切り出し先 Next.js アプリの API Routes と UI である。

| モード | 発生タイミング | 挙動 |
|---|---|---|
| `ANTHROPIC_API_KEY` が未設定 | デプロイ直後・意図的に AI 機能を使わない人 | 起動時に判定し、AI 機能全体を最初から disabled 表示 |
| キーが無効/失効（401 系） | 入力ミス・停止等 | 該当呼び出しだけ失敗として扱い、コア機能には伝播させない |
| レート制限/一時エラー（429/5xx） | 無料枠超過・Anthropic 側障害 | リトライは任意。失敗してもコア機能のコードパスを汚染しない |
| ネットワーク到達不可 | 一時的な通信障害 | AI 呼び出しの timeout がコア機能のレスポンスを巻き込まない |

- フラグの単一算出点: `hasAnthropicKey = !!process.env.ANTHROPIC_API_KEY` のようなヘルパーを 1 箇所（例: `lib/ai/isEnabled.ts`）に置き、全 AI 関連ルート・コンポーネントがそこだけを参照する。クライアントにキーの有無を直接晒さず、サーバーが `aiEnabled: boolean` を返す
- エンドポイント分離: コア機能の API route は AI クライアントを import しない。AI 機能は別エンドポイントに隔離し、そちら側だけが Anthropic 呼び出しを持つ
- AI 呼び出しは常に try/catch。失敗時は構造化エラーを返すだけで、プロセスやリクエストを落とさない
- UI 側は Error Boundary で AI セクションを囲む。AI 側がクラッシュしてもコア機能の画面は正常表示を保つ
- AI 無効時は該当 UI を disabled 表示＋「Anthropic キーを設定すると使えます」の案内に差し替える

着手承認が出た場合の順序:

1. 雛形の最初に `lib/ai/client.ts`（キー無しなら `null`）と `lib/ai/isEnabled.ts` を用意する
2. コア機能を先に実装し、Anthropic キーを unset にした環境で通し確認する
3. AI 機能を後から追加し、キーを外した状態でコア機能が壊れていないことを毎回確認する
4. disabled 表示と案内文を実装する
5. 無効キーで 401/429/timeout を起こし、コア機能側に影響が出ないか確認する

受け入れ条件:

- `ANTHROPIC_API_KEY` を unset にした状態で、テキストのフレーズ練習と学習記録（お気に入り登録）を最初から最後まで完了できる。音声機能は無い
- 同じ状態で AI 機能の UI が disabled 表示と案内文になり、クラッシュ・白画面・未処理エラーが出ない
- 有効なキーで稼働中のセッションからキーを無効な値に変更しても、コア機能側の操作はエラーにならない
- AI 呼び出し失敗（401/429/timeout）が、コア機能側の他の API エンドポイントのレスポンスに影響しない

基礎会話OSを習得した後、黒澤さんが日本語で使っている次の思考順序を、短い英語で再現できる訓練には価値がある。Phase 番号は未決である。設計正本の Phase 2（外資面接）の定義そのものではない。`speak-kit` のコア機能でもない。載せるリポジトリは未決である。

ファイル名に残っていた「Core30」は初期構想の呼称であり、現在の Skill 件数や突破条件を表さない。現行 Phase 1 catalog は 50 Skill で、進級は件数ではなく versioned Learner Phase Gate が Evidence から判定する。

```text
結論を置く
→ 理由を述べる
→ 仮説を置く
→ 反証条件を示す
→ 次の行動を決める
```

これは現時点で Phase 1 Core へ Skill を足すだけの話ではない。次の二層を分けて扱う。

1. `I think ...`、`The reason is ...`、`For now, ...` のような再利用可能な言語部品。既存エンジンの Skill / Exercise 候補になり得る。
2. 複数の部品を「結論→理由→仮説→反証→行動」の順で組み立てる談話能力。1 個の Skill ではなく、Scenario、Rubric、複数 Skill の構成として観測する。

有力な設計は、新しい Engine や独自 Phase を作ることではなく、既存の適応訓練エンジン上に将来の談話訓練パックとして載せることである。Phase 1 / 2 / 3 のどこへ置くかは、Phase 1 の実測と要求される Capability を確認してから決める。

#### 何を学ばせたいか

目的は高度な表現を増やすことではない。自分の判断過程を、簡単な英語のまま相手が追える形にする。

```text
I think ...
The reason is ...

In my case, ...
So my guess is ...

But if ..., then ...
That would change my view.

For now, ...
The next step is ...
```

上記は候補の説明例であり、そのまま Exercise の問題文・唯一の正解・未解決 placeholder として使わない。

#### 現行 catalog との関係

legacy v1 seed の完成文を、現行 v2 の Skill identity とみなしてはならない。v2 では owner review 済みの対応表を介し、抽象 Skill と具体 Exercise を分離済みである。

| stable key | 現行 v2 Skill | 意味 | この構想との関係 |
|---|---|---|---|
| `PERSONAL_CASE` | `In my case, {statement}.` | 自分の場合を述べる | 言語部品の一つ。思考手順全体ではない |
| `CORRECTION_MEAN` | `I don't mean {a}. I mean {b}.` | 誤解を訂正する | 論点修正に使えるが、反証能力そのものではない |

legacy の `In my case, I work from home.` や `I don't mean today. I mean tomorrow.` は具体 Exercise 側の素材であり、この談話訓練が実装済みであることを意味しない。

#### Skill 候補と談話上の役割

以下は採用済み Skill ではなく、重複・粒度・使用頻度を review するための候補分類である。

| 役割 | intent 候補 | 表現例 |
|---|---|---|
| 立場を置く | `STANCE` | `I think ...` / `From my point of view, ...` |
| 論点を限定する | `ISSUE_FRAMING` | `The problem is ...` / `It's not about A. It's about B.` |
| 仮説を置く | `HYPOTHESIS` | `My guess is ...` / `It could be ...` |
| 条件付きで修正する | `CONDITIONAL_REVISION` | `But if ..., then ...` / `That would change my view.` |
| 次の行動を示す | `NEXT_ACTION` | `For now, ...` / `The next step is ...` |

採用時は、表現例の数だけ Skill を作らない。同じ意味・用途を持つ語彙差は Exercise または accepted variant で扱い、Skill は別文脈で再利用・集計できる粒度にする。`A`、`B`、`...` を含む型は Skill の説明には使えても、Exercise materialize 時に具体値へ解決できなければ提示・採点しない。

#### 観測設計の仮説

言語部品単体は現行 Capability で観測できる。

- `CONTROLLED_RECALL`: 手掛かりから表現を取り出せるか
- `SLOT_REPLACEMENT`: 文脈に合わせて slot を差し替えられるか
- `CONTRAST_SELECTION`: 近い表現から用途に合うものを選べるか
- `FREE_PRODUCTION`: 話題と目的から自力で構成できるか
- `CONVERSATION_USAGE`: 会話中に自発使用できるか
- `RETENTION_1D` / `RETENTION_7D` / `RETENTION_30D`: 間隔を空けても保持できるか

思考順序全体を測るには、少なくとも次の Rubric dimension が必要になる可能性がある。

- 結論が先に示されたか
- 理由が結論を支えているか
- 仮説と事実を区別したか
- 反証・修正条件を示したか
- 次の行動へ接続したか
- 相手が追える短さと一貫性を保ったか

これらはまだ正式 Capability ではない。既存 `FREE_PRODUCTION` / `CONVERSATION_USAGE` の Rubric dimension で十分か、独立 Capability が必要かを fixture と実会話で検証してから決める。

#### Phase と Gate

- 「Core30 突破」や Skill 件数を開始条件にしない。
- 現行 `phase1-gate-v2` をこの構想のために変更しない。
- Phase 1 の意味成果を支える小さな言語部品は Phase 1 catalog 候補になり得る。
- 談話構成そのものは、Phase 2 / 3 の Scenario や独立した post-Phase-1 track の方が適切な可能性がある。
- どこへ置く場合も、Engine Release Gate と Learner Phase Gate を混同しない。

この構想を Phase 1 Gate へ含めるには、基礎会話OSの成果に不可欠であること、既存 Capability で再計算可能に判定できること、現在の学習負荷を不当に広げないことを証明する必要がある。

#### 破綻条件

- 「黒澤思考OS」を根拠なく新しい Engine や Phase として実装する
- 個人の話し方を普遍的な学習者モデルや唯一の正解へする
- 複数文の談話構成を 1 つの Skill identity へ押し込む
- legacy の具体英文を現行 Skill と誤認する
- 表現例や placeholder をそのまま出題・採点する
- AI が文章を高く評価しただけで新 Skill や新 Capability を確定する
- Rubric dimension と Capability と Weakness Type を同じ enum として扱う
- 現行 Phase 1 Gate を実測なしに拡張する

#### この節を実装 task へ昇格する条件

1. Phase 1 の実学習データから、談話構成不足が反復するボトルネックとして確認される。
2. 既存 50 Skill との重複を owner review し、追加する atomic Skill 候補を確定できる。
3. 完成 prompt、reference 例、accepted variant、Rubric を持つ Exercise fixture を作れる。
4. `FREE_PRODUCTION` と `CONVERSATION_USAGE` で十分か、新 Capability が必要かを比較できる。
5. 採用先を Phase 1 拡張、Phase 2 / 3 content、別 track のいずれかに明示できる。
6. Gate へ影響させる場合、versioned policy 変更と既存 Evidence への影響を説明できる。

### Phase 1 にすでに入っているもの
